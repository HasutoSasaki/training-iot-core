# ベンチプレス分析 実装計画

[bench-press-analysis.md](bench-press-analysis.md) の提案を、このリポジトリで順に実装するための計画です。

## 決定事項

| 項目 | 決定 |
| --- | --- |
| 装着位置 | バーベルのシャフト、プレートの内側（スリーブ付け根側）。1 台から始める |
| 装着向き | 端末の長辺をバーの長軸に合わせ、画面を上向きに固定する |
| サンプリング | 100 Hz（現行 10 Hz） |
| 送信単位 | 0.5 秒ごとに 50 サンプル（現行 1 秒ごとに 10 サンプル） |
| 値の表現 | 加速度は mg、角速度は 0.1 dps の整数（現行 g / dps の小数 4 桁） |
| スキーマ | `schema_version` を 2 に上げる。キー名は v1 と同じにして Glue テーブルを流用する |

### ペイロードの見込み

| 形式 | 1 サンプル | 50 サンプル + ヘッダー |
| --- | --- | --- |
| v1（小数 4 桁） | 95 バイト | 約 5.0 KiB（上限超過） |
| v2（整数） | 75 バイト | 約 4.0 KiB（上限 4.5 KiB に対し約 500 バイトの余裕） |

送信は 1 秒に 2 メッセージになります。1 時間のトレーニングで約 7,200 メッセージで、IoT Core と Firehose の課金は 5 KiB 単位のメッセージ数で決まるため、個人利用では無視できる範囲です。

## スキーマ v2

```json
{
  "schema_version": 2,
  "device_id": "m5sticks3-01",
  "session_id": "2026-09-13T10:00:00+09:00",
  "set_id": 3,
  "placement": "barbell",
  "captured_at": "2026-09-13T10:05:12+09:00",
  "batch_start_ms": 1757725512340,
  "sequence": 412,
  "sampling_hz": 100,
  "samples": [
    { "offset_ms": 0, "ax": -12, "ay": 988, "az": 123, "gx": -1235, "gy": 123, "gz": -12 },
    { "offset_ms": 10, "ax": -10, "ay": 991, "az": 120, "gx": -1198, "gy": 130, "gz": -9 }
  ]
}
```

| フィールド | 変更 | 意味 |
| --- | --- | --- |
| `schema_version` | 1 → 2 | 分析側は v1 と v2 で単位を切り替える |
| `set_id` | 追加 | ボタン A の押下で +1。0 はセット外（ラック上、休憩） |
| `placement` | 追加 | `barbell`、将来 `wrist_left` などを追加。ファームウェアの定数 |
| `batch_start_ms` | 追加 | バッチ先頭サンプルの Unix epoch ミリ秒。`offset_ms` を足すと各サンプルの絶対時刻 |
| `captured_at` | 維持 | 人が読むための秒精度の時刻。分析では `batch_start_ms` を使う |
| `sampling_hz` | 10 → 100 | 公称値。実際の間隔は `offset_ms` の差で確認する |
| `ax` `ay` `az` | 単位変更 | mg の整数。1000 が 1 g |
| `gx` `gy` `gz` | 単位変更 | 0.1 dps の整数。10 が 1 dps |

`ax` などのキー名を変えないのは、Glue テーブルの `samples` 構造体（`double` 型）をそのまま使うためです。JSON の整数は `double` 列として読めます。

## ステップ

### ステップ 1: ドキュメント（この PR）

- 提案と実装計画を `docs/` に置く。
- 完了条件: 装着位置、レート、送信単位、スキーマ v2 が文書で決まっている。

### ステップ 2: ファームウェア v2

対象: `firmware/m5sticks3-telemetry/src/main.cpp`

- `SAMPLING_HZ` を 100、`SAMPLES_PER_BATCH` を 50 にする。
- `ImuSample` の 6 値を `int16_t` にし、取得時に `g × 1000`、`dps × 10` を四捨五入して格納する。
- `appendSampleJson` を整数フォーマットに変え、`schema_version` を 2 にする。
- `batch_start_ms` を `gettimeofday` から求める（NTP 同期済みなのでミリ秒が取れる）。
- `placement` 定数と `set_id` を追加し、ボタン A の押下で `set_id` を +1 する。画面にセット番号を出す。
- サンプリングのタイミングは `millis()` の差分ではなく「次の予定時刻」を積み上げる方式にして、10 ms 間隔のドリフトを防ぐ。
- `M5.Imu.update()` の戻り値で新しいデータが来たときだけサンプルを取り、同じ値の重複を避ける。
- 画面更新は 250 ms のままだが、描画にかかる時間がサンプル間隔を乱す場合は更新頻度を下げる。

確認方法:

- シリアルログに `offset_ms` の差分の最小・最大を出し、10 ms ± 2 ms に収まることを見る。
- 送信バイト数を表示し、4,500 バイト未満であることを見る。
- 机に置いた静止状態で鉛直軸が約 1000 mg、他の軸が 0 付近であることを見る。

リスク: MQTT の送信や TLS 処理がループを 10 ms 以上止め、サンプル間隔が乱れる可能性があります。乱れが大きい場合は、IMU 取得を FreeRTOS タスクに分けてキューで渡す構成に変えます。まずは単純な実装で計測し、必要になったら分けます。

### ステップ 3: AWS 側とスキーマ文書

対象: `infra/lib/training-iot-stack.ts`、`docs/telemetry-schema.md`

- Glue テーブルに `set_id`（int）、`placement`（string）、`batch_start_ms`（bigint）を追加する。`samples` 構造体は変更しない。
- `docs/telemetry-schema.md` を v2 に更新し、v1 との単位の違いを表で残す。
- `pnpm typecheck` と `pnpm synth` を通してからデプロイする。

確認方法: 1 セット送信後、Athena で `schema_version = 2` の行が取れ、`cardinality(samples)` が 50 であることを見る。

### ステップ 4: 分析スクリプト

対象: `analysis/`（Python）

- Athena から `session_id` と `set_id` で 1 セット分を取り出し、`samples` を展開して 1 行 1 サンプルの表にする。
- `schema_version` に応じて g / dps に戻す。
- セット冒頭の静止区間から重力ベクトルを推定し、鉛直・前後・左右へ再投影する。
- 鉛直加速度を積分して速度を求め、ゼロクロスでレップを切り出す。レップごとに速度を 0 にリセットする。
- レップごとに MCV、ピーク速度、ROM、下降・停止・上昇時間、傾き角、前後ブレを CSV に出す。

確認方法: スマートフォン動画（60 fps 以上）でレップ数とボトムの時刻を目視し、検出結果と比べる。

### ステップ 5: Grafana

- 鉛直加速度、鉛直速度、傾き角の時系列パネルを追加する。
- `set_id` で絞るテンプレート変数を追加する。

### ステップ 6: 端末での即時表示（任意）

- 端末で鉛直速度のゼロクロスを検出し、レップ数と直前レップの MCV を画面に出す。
- ステップ 4 でアルゴリズムが固まってから移植する。

## 変更しないこと

- IoT Rule、Firehose、S3 の構成。メッセージ数が増えるだけで構成は変わらない。
- MQTT トピックと Thing ポリシー。
- v1 で保存済みのデータ。分析側で `schema_version` を見て単位を切り替える。
