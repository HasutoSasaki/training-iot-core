# ベンチプレスのフォーム分析: デバイス取付位置と使用データの提案

現在の基盤（M5StickS3 / BMI270 の 6 軸 IMU を 10 Hz で取得し、1 秒ごとに 10 件を AWS へ送る構成）を前提に、ベンチプレスのフォームを分析するために「どこに端末を付けるか」「どのデータを使うか」を整理した提案です。実機で取得したデータを見ながら見直すことを前提にしています。

## 1. ベンチプレスで「フォーム」として見たいもの

| 観点 | 何が分かると嬉しいか | IMU で測れるか |
| --- | --- | --- |
| 挙上速度（VBT: 平均コンセントリック速度・ピーク速度） | 疲労度、RPE の推定、セット内の速度低下率、フォーム崩れの前兆 | ◎ バー装着 1 台で可能 |
| バーの左右の傾き | 左右差、利き腕側の先行、片側の潰れ | ◎ バー装着 1 台で可能 |
| バーの前後ブレ（バーパス） | ラックアウト位置の安定、J カーブの再現性 | ○ レップ単位の積分で傾向は見える |
| テンポ・一貫性 | 下降時間、ボトム停止時間、上昇時間、レップ間のばらつき | ◎ バー装着 1 台で可能 |
| バウンド（胸で跳ねる） | ボトムでの衝撃の有無 | ◎ 鉛直加速度のスパイクで検出 |
| 手首の返り・バーの回転 | グリップの安定 | ○ バー長軸まわりのジャイロ |
| 肘の開き（フレア）・前腕の傾き | 肩への負担、軌道の再現性 | △ 手首・上腕への追加装着が必要 |
| 背中のアーチ・レッグドライブ | 体幹の安定 | △ ベンチ上では体幹はほぼ動かず、IMU では見づらい |

上半分（速度・傾き・テンポ・バウンド）は **バーに付けた 1 台** で分析できます。IMU をバーに固定して速度プロファイルを求める手法は、動画基準と比較して平均差 0.00 ± 0.04 m/s、一致限界 0.09 m/s 未満という検証結果が報告されています（Rum ほか, Sensors 2022）。一方、前腕（手首）装着の商用 IMU はベンチプレスの平均速度で大きな誤差が報告されており、バー速度を見る目的では手首装着は不利です。

## 2. 取付位置の候補と評価

| 候補 | 分かること | 課題 | 評価 |
| --- | --- | --- | --- |
| **A. バーベルのシャフト**（プレートの内側、スリーブ付け根側） | 挙上速度、ROM、左右の傾き、前後ブレ、テンポ、バウンド、バー回転 | 固定方法、装着向きの再現性、プレート交換時に外れないこと | **第一候補** |
| B. 手首（片側または両側） | 手首の返り、前腕の傾き、左右の動きの差 | バー速度としての精度が低い。体の回転成分が混ざる | 第二段階で追加 |
| C. 上腕（肘の上） | 肘の開き（フレア）角、上腕の軌道 | 皮膚・筋肉の動きでノイズが乗る。2 台以上必要 | 第三段階 |
| D. 胸（胸骨） | アーチの変化、レッグドライブでの体の浮き | ベンチに固定された体幹は動きが小さく、分析価値が低い | 見送り |
| E. ベンチ台 | ベンチの揺れ | フォーム分析にはほぼ寄与しない | 見送り |

### A. バーベル装着の詳細

- **位置**: シャフトの片側、プレートの内側（スリーブ付け根側）に付けます。中央は胸に当たるため避けます。バーは剛体なので、回転が小さい範囲では中央からずらしても直線加速度はほぼ同じです。左右の傾き角も位置に依存しません。
- **向き**: 端末の 1 軸をバーの長軸（左右方向）に合わせ、画面が上を向くように固定します。これで「鉛直」「前後」「左右（バー長軸）」の 3 軸が端末軸に対応し、分析時の座標変換が単純になります。
- **固定**: シリコンバンドまたはベルクロで端末の全周を留めるか、3D プリントしたクランプにマウントします。緩い固定は高周波の振動ノイズになります。
- **左右差を見る場合**: 傾き角（バー長軸まわりではなく、前後軸まわりのロール）は 1 台で分かります。左右それぞれの速度差まで見たい場合は、両端に 1 台ずつ付けて同一 `session_id` で同時計測します。

### 端末の軸を装着状態で決める

M5StickS3 の軸定義（どの軸が長辺か）は実機で確認します。装着後にラックに置いた静止状態で重力ベクトルを 1〜2 秒取得し、それを「鉛直」の基準にします（ラックキャリブレーション）。装着角度が多少ずれても、この基準を使えば鉛直・前後・左右へ再投影できます。

## 3. 使用するデータと導出指標

### 生データ（現行スキーマで取得済み）

| 生データ | ベンチプレスでの意味 |
| --- | --- |
| 鉛直方向の加速度（重力除去後） | 挙上の加減速。積分して速度・変位を求める主役 |
| 前後方向の加速度 | バーパスの前後ブレ |
| 左右方向（バー長軸）の加速度 | 通常は小さい。大きい場合は装着ずれかバーの横滑り |
| 前後軸まわりの角速度（ロール） | バーの左右の傾きの変化。積分すると傾き角 |
| バー長軸まわりの角速度 | 手首の返り、バーの回転 |
| 鉛直軸まわりの角速度（ヨー） | バーの水平面内の回転。通常は小さい |

### 導出指標

| 指標 | 計算方法 | 用途 |
| --- | --- | --- |
| レップ区切り | 鉛直速度のゼロクロス（負→正がボトム、正→負がトップ） | 全指標の前提 |
| 平均コンセントリック速度（MCV） | ボトムからトップまでの変位 ÷ 時間 | 負荷管理、疲労 |
| ピーク速度 | 上昇局面の速度最大値 | 爆発力 |
| ROM（可動域） | 上昇局面の変位 | 一貫性、ハーフレップ検出 |
| 下降時間・ボトム停止時間・上昇時間 | 速度ゼロクロス間の時間 | テンポ |
| バウンド指標 | ボトム付近での鉛直加速度のスパイク振幅 | 胸で跳ねているか |
| 左右傾き角 | 静止時は `atan2(左右g, 鉛直g)`、動作中はロール角速度を積分しレップ端で補正 | 左右差 |
| 前後ブレ量 | 前後加速度をレップ内で 2 回積分（レップ端で速度 0 拘束） | バーパス |
| セット内速度低下率 | (1 レップ目 MCV − 最終レップ MCV) ÷ 1 レップ目 MCV | 疲労、追い込み度 |

### ドリフトへの対策

加速度を積分すると速度・変位に誤差が蓄積します。ベンチプレスはレップの端（トップ・ボトム）で速度がほぼ 0 になるので、レップごとに速度を 0 にリセットし、レップ内の線形ドリフトを差し引く方法が現実的です。セット全体を連続積分しないことが重要です。

## 4. 現行構成で足りない点と変更提案

### サンプリングレートを上げる（最優先）

現在の 10 Hz では不足します。コンセントリック局面は 0.5〜1.5 秒程度で、ピーク速度やバウンドのスパイクは 0.1 秒以下の現象です。IMU による VBT の研究では 100〜1000 Hz が使われています。**最低 50 Hz、推奨 100 Hz** を目標にします。BMI270 自体は 100 Hz 以上で動作でき、M5Unified の既定設定も 100 Hz 前後・±8 g とされています（M5Unified の実装依存のため、実機で `update()` の更新間隔を確認します）。

### ペイロード上限（4.5 KiB）との両立

現行の 1 サンプルは小数 4 桁で約 95 バイトです。100 Hz では 1 秒分が上限を超えます。次のいずれかで収めます。

| 案 | 内容 | 1 サンプルの目安 | 100 Hz での送信 |
| --- | --- | --- | --- |
| 1 | 小数を 3 桁にし、バッチを 0.5 秒（50 件）にする | 約 89 バイト → 50 件でヘッダー込み約 4.6 KiB | 上限を超える。40 件（0.4 秒）なら収まる |
| **2** | 加速度を mg、角速度を 0.1 dps の整数で送る | 約 75 バイト → 50 件でヘッダー込み約 4.0 KiB | **推奨**。0.5 秒ごとに 1 メッセージ |
| 3 | 端末でレップ単位に集約したサマリだけ送る | 小さい | 生データが残らないため初期段階では不採用 |

案 2 では 1 秒あたり 2 メッセージになりますが、IoT Core・Firehose の課金は 5 KiB 単位のメッセージ数なので個人利用では無視できる範囲です。整数化する場合は `schema_version` を 2 に上げ、単位を [telemetry-schema.md](telemetry-schema.md) に明記します。

### 時刻とセッションの粒度

- `captured_at` は秒精度のため、バッチをまたいだ連結で最大 1 秒の曖昧さが出ます。バッチ開始時刻を Unix epoch ミリ秒（例: `batch_start_ms`）で持たせ、`offset_ms` を足して各サンプルの絶対時刻を決められるようにします。
- `session_id` は起動時に 1 回決まります。ボタン A の押下でセット開始・終了を記録し、`set_id`（セット番号）をペイロードに加えると、Athena でセット単位に絞れます。
- 装着位置を区別するため `placement`（`barbell` / `wrist_left` / `wrist_right` など）を加えます。複数台で同時計測するときに必須です。
- 任意で `load_kg` を持たせると、負荷と速度の関係（Load-Velocity プロファイル）が後から引けます。

### 加速度レンジ

ベンチプレスでバーに生じる加速度は重力を含めても 2 g 程度です。±8 g では分解能を無駄にするため、可能なら ±4 g に下げます。なお M5Unified の BMI270 でレンジ飽和時に符号が反転する報告があります（M5Unified Issue #230）。飽和しない負荷では影響ありませんが、バーをラックに乱暴に戻したときのスパイク前後は分析から除外します。

### 端末側の即時表示

現在の設計思想（判定は端末、クラウドは保存）に沿って、端末には「レップ数」と「直前レップの MCV」を表示するのが実用的です。鉛直速度のゼロクロス検出は 100 Hz でも軽量に動きます。

## 5. 分析手順（事後）

1. Athena で `session_id`（と `set_id`）を指定して `samples` を展開し、pandas に読み込む。
2. セット開始直後の静止区間から重力ベクトルを推定し、各サンプルを鉛直・前後・左右へ再投影して重力を除く。
3. 鉛直加速度を 0.5〜10 Hz 程度のバンドパス（または移動平均）で整え、積分して鉛直速度を得る。
4. 速度のゼロクロスでレップを切り出し、レップごとに速度を 0 にリセットして再積分する。
5. レップごとに MCV・ピーク速度・ROM・テンポ・傾き角・前後ブレを計算し、セット内の推移をまとめる。
6. Grafana には「鉛直加速度」「鉛直速度」「傾き角」の時系列と、セット内のレップ別 MCV を並べる。

## 6. 検証方法

- **速度**: スマートフォンで真横から 60 fps 以上で撮影し、バー端のマーカーを Kinovea や Tracker で追跡して速度を求め、IMU の MCV・ピーク速度と比較する。
- **傾き**: バーの片側だけプレート台に載せて既知の角度を作り、静止時の傾き角と照合する。
- **レップ検出**: 動画でレップ数とボトム時刻を目視確認し、検出結果と突き合わせる。

## 7. 実装ステップ（このリポジトリでの順序）

詳細は [bench-press-implementation-plan.md](bench-press-implementation-plan.md) にまとめています。

1. ファームウェア: サンプリングを 100 Hz、バッチを 0.5 秒にし、値を整数化する。ボタン A でセット開始・終了、`placement`・`set_id`・`batch_start_ms` を追加する。
2. `docs/telemetry-schema.md` を schema_version 2 に更新する。
3. CDK: Glue テーブルの `samples` 構造体と上位カラムに新フィールドを追加する。
4. `analysis/`: Athena から読み込んでレップ検出・MCV を計算する Python ノートブックを置く。
5. Grafana: 鉛直加速度・速度・傾き角のパネルを追加する。
6. 手首装着の 2 台目を追加し、バー装着と同時計測して肘・手首の指標を検討する。
